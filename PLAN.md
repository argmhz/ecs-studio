# Plan: browserbaseret ECS-spilmotor

Status: M0 tekniske valg er afklaret. T001–T004, T101–T111, T201–T212, T301–T304, T306–T309 og T312–T335 er gennemført. T305 og T311 er udsat. Seneste fulde Chromium-editor-suite bestod 53/53 tests efter T334. Desuden består 5/5 WebGL-browserflows og 20 rendering-unit-tests.

## Mål og beslutninger

En visuel spilmotor til begyndere og udviklere med lokal projektlagring, ECS, WebGL og både kodebaseret og nodebaseret scripting. Første udgivelse skal være en bred 2D-motor; senere udvides den til stiliseret 3D.

| Område | Beslutning |
| --- | --- |
| Målgruppe | Begyndere og udviklere |
| Editor og platform | Editor på computer; spil på computer og mobil |
| Scripting | TypeScript/JavaScript og visuelle noder med fælles API, events og variabler |
| Lagring | Lokale projekter uden obligatorisk konto |
| Publicering | Webeksport og integration med brugerens hosting; egen hosting senere |
| Rendering og fysik | Eksisterende biblioteker bag egne integrationer; WebGL påkrævet |
| ECS | Egen kerne, indledningsvis sparse sets |
| Multiplayer | Private rum til 2–8 spillere med autoritativ server |
| Samarbejde | Projektfildeling først; samtidig redigering senere |
| Terræn | Tilemaps med lag, kollision og automatisk valg af nabofliser |
| Animation | Spriteanimation og tidslinjer først |
| Plugins | Komponenter, scripts, asset-import og editorpaneler |
| Licens | Open source som mål; MIT foreslået, offentliggørelse besluttes separat |

## Editorens arbejdsgang

- Følg velkendte Unity/Unreal-principper: objekter, komponenter, hierarki, inspector, prefabs, drag-and-drop og Play/Pause/Step. ECS er fundamentet, men ikke påkrævet begyndervokabular.
- Engelsk UI og API; dansk projektdokumentation. Kode og nodegrafer åbnes i faner.
- Scripts og nodegrafer sættes på objekter; ECS-systemer er en avanceret mulighed.
- Manuel gemning kombineres med lokal gendannelse og tydelig markering af ugemte ændringer.
- Start med tomt projekt eller kommenteret spilskabelon. Genindlæsning af kode under Play og AI-completion ligger uden for første implementation.

## Taskstatus og færdigkriterier

- `[ ]` betyder ikke færdig. Tilføj `I gang` eller `Blokeret: årsag` på tasken efter behov.
- `[x]` betyder implementeret og verificeret mod taskens acceptkriterier.
- Hver implementering skal have relevant validering og nødvendig dokumentation. Registrér væsentlige valg i docs/decisions/.
- T001–T004, T101–T111, T201–T212 og T301–T304/T306–T309 er gennemført; T305 er udsat. Se tasks for validering og kendte begrænsninger.

## M0 — Tekniske valg og projektopsætning

- [x] **T001 — Afprøv rendering, fysik og editorstack.** Three.js/Rapier/Monaco-prototype og React-inspectorpilot er afprøvet; stackvalg og bundlemålinger er dokumenteret i [ADR 0001](docs/decisions/0001-editor-stack.md). React vælges til editorens UI-paneler; WebGL viewport, simulation og Monaco forbliver separate integrationsflader. Typecheck, produktionsbuild og fokuseret Chromium-test bestået via Docker. Loadtidsmål og browsersupportmatrix hører til T004.
- [x] **T002 — Afprøv scripting og isolering.** `runSandboxed` bruger en disposable `iframe sandbox="allow-scripts"` uden `allow-same-origin`, CSP med `connect-src 'none'` og en nested Blob Worker. UI-ejet timeout/cancellation fjerner hele iframen. Input og output er JSON-kopier med 256 KiB standardloft; source har samme loft. `runNodeGraph` håndhæver højst 10.000 deklarative nodebesøg pr. kørsel. Typecheck, 3 nodegraf-unit-tests og 15 Chromium-editorchecks bestået; checks afprøver worker-return/exception, timeout, cancellation, opstartsfejl, u-klonbart resultat, payloadlofter, opaque origin, DOM/storage/netværksbegrænsning, gentagne kørsler og fortsat UI-respons. Hukommelsesforbrug kan ikke hårdt begrænses, og sandboxen er ikke en garanti mod browserfejl. Plugins med editorrettigheder er betroet kode. Se [ADR 0002](docs/decisions/0002-script-isolation.md).
- [x] **T003 — Opret workspace og kvalitetstjek.** npm-workspaces er opdelt i editor, core, runtime, rendering, browserintegration, scripting og eksempelspil. Browserprototypen blev flyttet ind uden ændring af Play-mode-testene. `npm ci`, typecheck, produktionsbuild og tre Playwright/Chromium-checks bestod; npm audit viste 0 sårbarheder. Docker Compose og README beskriver kommandoerne. Det daværende åbne UI-frameworkvalg blev afklaret efterfølgende i T001.
- [x] **T004 — Fastlæg support- og ydelsesmål.** [ADR 0034](docs/decisions/0034-browser-support-and-performance-budgets.md) fastlægger desktop-/mobilmatrix, browserkrav, testprofiler og budgetter for opstart, frame time, bundle og projekter. `npm run test:browser-matrix` tester IndexedDB-projektgendannelse i Chromium/Firefox/WebKit samt WebGL 2 og Play i Chromium/WebKit; Linux-headless Firefox WebGL er eksplicit sprunget over og kræver GPU-backed release-check. Eksportens spilflow er aktuelt kun dækket i Chromium. `npm run test:renderer-browser` afprøver WebGL-context recovery og en 1.000-sprite batching/timingprofil. `.ecsproj`-download/import er eksisterende manuel fallback til IndexedDB-kvote-/lagringsfejl. Typecheck og begge browserchecks bestået via Docker. Bundlebudgetter er målt; frame-time og opstartstiderne er mål, som skal verificeres på referencehardware i T311.

Exit: stack og væsentlige tekniske risici er afprøvet, og udviklingsmiljøet fungerer.

## M1 — Fundament og grundeditor

Afhænger af M0.

- [x] **T101 — ECS-kerne.** Entities med generationssikre handles pr. World, sparse-set komponentlagre, snapshotqueries, resources og command buffer med pending handles. 13 unit tests passerer, inklusive generation, cross-world, storage, query og command-buffer fejltilstande. Typecheck bestået. Se [ADR 0003](docs/decisions/0003-ecs-core.md) og `packages/core/README.md`. Scheduler og sceneformat hører til senere tasks.
- [x] **T102 — Scheduler og simulation.** Stabil rækkefølge efter eksplicit order, fast tidssteg, render-interpolation-alpha, pause/enkelttrin og loft på frame-delta samt catch-up; fejlede ticks gentages ikke automatisk. 7 runtime- og 13 core-unit tests, typecheck og produktionsbuild bestået. Se [ADR 0004](docs/decisions/0004-simulation-scheduler.md).
- [x] **T103 — Komponentschemas og sceneformat.** `@ecs/scene` forbinder schemas med ECS-komponenter, inspector-felter, validering, stabile scene-/entity-/assetreferencer og JSON scene-roundtrip. Scener og komponentdata er versionsmærkede med eksplicitte migrationer; ukendte komponenter og ugyldige data giver fejl med sti. 6 scene-tests, 7 runtime-tests, 13 core-tests, typecheck og produktionsbuild bestået. Se [ADR 0005](docs/decisions/0005-scene-schema-format.md).
- [x] **T104 — Hierarki og transforms.** `SceneHierarchy` håndterer parent/child med stabile scene-ID’er, lokale 2D position/rotation/skala og globale affine transforms. Reparenting bevarer lokal transform og afviser selv-parenting, ukendte entities og cykler uden delvise ændringer. Scene load/save validerer referencer og cykler gennem schema-metadata. 13 scene/hierarki-tests, 7 runtime-tests, 13 core-tests, typecheck og produktionsbuild bestået. Se [ADR 0006](docs/decisions/0006-hierarchy-transforms.md).
- [x] **T105 — Asset pipeline.** `@ecs/assets` importerer billed-/lydformater, gemmer versioneret manifest med bytes nøglede efter stabile asset-ID’er, bevarer ID ved reimport/flytning og skelner mellem manglende og ukendte filer. `AssetStore` gør persistent project storage adapterudskiftelig; browserens lokale persistence kobles i T109. 7 asset-tests, 13 scene-tests, 7 runtime-tests, 13 core-tests og typecheck bestået. Se [ADR 0007](docs/decisions/0007-asset-catalog.md).
- [x] **T106 — WebGL-renderer til 2D.** `@ecs/rendering` bruger Three.js WebGL 2 med sprites, ortografisk kamera, stabil sortering, contiguous texture batching, capped-DPR resize og context loss/restore. Asset-ID’er forbindes til Three textures via adapter, og sprite-components adapteres fra `World`/`SceneHierarchy`. 6 renderer unit tests, Chromium WebGL-smoketest, typecheck, produktionsbuild og 3 eksisterende editor-browserchecks bestået. Se [ADR 0008](docs/decisions/0008-webgl-2d-renderer.md).
- [x] **T107 — Editorens grundlayout.** Unity/Unreal-inspireret layout med hierarki, Scene/Game/Code-faner, schema-baseret inspector og Assets/Console-workbench. Scene-viewport, hierarki og inspector deler ECS-World; importerede billeder kan tildeles sprite-komponenten. Paneler kan flyttes, størrelsesændres og nulstilles. Typecheck, produktionsbuild og 6 Chromium-editorchecks bestået. Game-fanens midlertidige physics preview og projektlagring er eksplicit adskilt til T110 og T109. Se [ADR 0009](docs/decisions/0009-editor-workbench.md).
- [x] **T108 — Sceneværktøjer og undo/redo.** Select/Move/Rotate/Scale-værktøjer, snapping, Local/Global orientering, multi-selection, genveje og kontekstmenuer styrer den ECS-baserede scene. Inspectorændringer, viewport-drag, oprettelse, duplikering, sletning, reparenting og sprite-assettilknytning registreres som sammenhængende handlinger i en bounded 100-command undo/redo-historik. Typecheck, produktionsbuild, 2 historik-unit-tests og 10 Chromium-editorchecks bestået. Browser-preview oprydning håndterer ændrede entity-sæt. Se [ADR 0010](docs/decisions/0010-scene-editing-history.md).
- [x] **T109 — Lokal projektlagring.** IndexedDB gemmer scene, assetmanifest og bytes pr. lokalt projekt-ID. Autosave med gemmestatus gendanner scenen ved genåbning; Save er eksplicit tilgængelig. Versionsmærkede `.ecsproj`-arkiver kan downloades/importeres med scene og assets og valideres før projektet åbnes. New Project opretter et separat lokalt projekt. Typecheck, produktionbuild, 4 editor-unit-tests og 12 Chromium-editorchecks bestået; browserchecks afprøver reload-gendannelse og fuld projektarkiv-roundtrip. Kodefanens indhold er endnu ikke del af projektformatet. Se [ADR 0011](docs/decisions/0011-local-project-storage.md).
- [x] **T110 — Play mode.** Play serialiserer/deserialiserer en separat ECS-scene og simulerer den i Game-viewet. Rapier-kald er et navngivet runtime-system på `FixedStepLoop` med fast 1/60 s step, loft på catch-up og frame-delta. Pause stopper ticks, Step kører præcis ét tick, og Resume fortsætter. Stop frigiver Rapier-world og loopreferencer og beholder inspector-/ECS-redigeringstilstanden. Typecheck, produktionsbuild, 4 editor-unit-tests og 12 Chromium-editorchecks bestået; Play-browsercheck verificerer tick-frysning, enkelttrin, sceneværdier efter Stop og gentagne start/stop uden ekstra canvas. Se [ADR 0012](docs/decisions/0012-play-mode-scene-copy.md).
- [x] **T111 — Første eksempelspil.** `examples/physics-playground/` er nu Physics Playground-eksempel med dansk guide til at redigere Player/Crate/Ground, teste fysik i Play, oprette et objekt, gemme og genåbne. En Chromium-workflowtest opretter og tilpasser Bonus Crate, kører Play, venter på autosave og bekræfter værdierne efter genindlæsning. Testen fandt og fikset, at Hierarchy-panelet ikke blev genopbygget efter indlæsning af objekter, der ikke fandtes i starter-scenen. Typecheck, produktionsbuild, 4 editor-unit-tests og 13 Chromium-editorchecks bestået. Eksemplet er en redigerbar fysiksandbox; gameplay-input og scripts følger senere. Se [eksempelguiden](examples/physics-playground/README.md).

Exit: en bruger kan oprette og gemme en scene, redigere objekter og starte og stoppe simulationen.

## M2 — Spilværktøjer og begge scriptformer

Afhænger af M1 og isoleringsvalget i T002.

- [x] **T201 — Fælles scripting-API.** `@ecs/scripting` definerer lifecycle-faser, schema-validerede inspector-properties, JSON-kopieret komponentadgang, events og idempotent afslutning. Kode- og nodeinvokationer bruger samme API; hosten anvender returnerede kommandoer efter schema-validering. Seks scripting-unit-tests, typecheck, produktionsbuild, 4 editor-unit-tests og 15 Chromium-editorchecks bestået. Se [ADR 0013](docs/decisions/0013-shared-script-api.md) og `packages/scripting/README.md`. Afviklingsrækkefølge og hostens anvendelse af output implementeres i T202/T203.
- [x] **T202 — TypeScript/JavaScript-scripting.** Monaco bruger lokale TypeScript-workers til syntax highlighting, diagnostics, hover og completion; engine-typer og `speed`-property genereres fra komponentschemas/scriptdefinition. Projektfiler kan oprettes, søges og deler globale symbols; filer og properties gemmes i projektformat v3, og v1/v2 migreres. `update(api)` transpileres i Monacos worker ved Play og kører i disposable sandbox-worker med 500 ms loft; schema-validerede kommandoer ændrer Play-kopien, Stop afbryder workers. Valideret med typecheck, produktionsbuild, 7 editor-unit-tests, 8 scripting-tests og alle 20 Chromium-editorchecks. Fejl før Play vises ved den relevante fil/linje; runtimefejl åbner filen og afslutter Play. Afhænger af T201. Accept opfyldt: kode kan redigeres og køres med inspector-properties, kildehenvisninger ved fejl og stop af fejlende eller fastlåst scriptkørsel. Begrænsninger: kun `update`-lifecycle, ingen ES-modulimporter og worker-oprettelse pr. scriptopdatering; gennemløb er ikke profileret, så ydelsesoptimering skal bygge på en senere måling. Se [ADR 0014](docs/decisions/0014-code-workspace-and-project-files.md).
- [x] **T203 — Visuel scripteditor.** Separat Nodes-fane med flytbare noder, SVG-forbindelser, typede porte, typevalidering, undo/redo og serialiseret projektgraf. Noder dækker update, JSON/number, variables, greater-than, branch, repeat, component read/write samt event payload/emit/subscribe; Play kører grafen via samme `ScriptApi` og schema-validerede kommandoer som kodescript. Repeat har 1.000 iterationers loft og hver kørsel 10.000 nodebesøgs loft. Arkivformat v4 migrerer v1–v3 og validerer grafer. Forbindelser oprettes nu ved klik på en output- og derefter input-port, kan fjernes ved klik på ledningen, og følger noder under træk; Nodes-manualen beskriver binding, eksekveringsflow og preview. Typecheck/build, 8 editor-unit-tests, 14 scripting-tests og fokuserede browserflows for nodeforbindelser passerer. Komponenttype-ID'er indtastes manuelt, og Inspector-felter genereres endnu ikke som individuelle noder. Samspil mellem flere scripts følger i T204. Se [ADR 0015](docs/decisions/0015-visual-script-graph-format.md).
- [x] **T204 — Samspil mellem scripts.** Play starter både `player.ts` og nodegrafen med separat state/subscriptions. Begge læser ved hvert script-update samme snapshot; kode kører før graf, kommandoer anvendes i den rækkefølge, og events går til abonnenter ved næste update. Physics Playground demonstrerer positionspayload fra kode til graf og tilbage til kode. Scripting-README og [ADR 0016](docs/decisions/0016-script-update-order-and-events.md) beskriver scheduler, forsinkelse og konfliktrækkefølge. Typecheck, build, 14 scripting-tests og 22 Chromium-checks bestået.
- [x] **T205 — Input actions.** `@ecs/runtime` indeholder DOM-uafhængigt action map med standardhandlingerne `moveX`, `moveY`, `jump`, `interact` og pressed/edge-state. Browser-preview samler fokuseret keyboard, mus/touch-pointer med canvas-normaliserede koordinater og tilsluttede gamepads; begge scriptformer modtager samme snapshot, og grafer har en Input Action-node. Eksempel-Player styres med A/D, W/S, piletaster og gamepad-stick. Typecheck, produktionsbuild, 9 runtime-tests, 17 scripting-tests, 8 editor-unit-tests og 23 Chromium-checks bestået. Gamepadbindings er afprøvet med simulerede samples; en fysisk gamepad og mobil-browser er ikke afprøvet. Se [ADR 0017](docs/decisions/0017-input-actions.md).
- [x] **T206 — 2D-fysik.** Schema-baserede `Physics2D` og `Collider2D` understøtter rigid bodies, box/circle, friktion, restitution, 16-bit collision group/mask og triggers med fast 1/60 s step. Collision-/trigger-events leveres til scripts i næste update. Play afstemmer runtime add/remove af Physics2D, Collider2D og SpriteRenderer2D med Rapier-/Three.js-ressourcer; Stop beholder redigeringsscenen. Inspector kan tilføje/fjerne valgfri schema-registrerede komponenter ved valg i komponentlisten; `Name` og `Transform2D` forbliver på alle sceneobjekter. Typecheck/build, 27 browserchecks, 8 editor-unit-tests og 17 scripting-tests passerer. Transformejerskab, eventrækkefølge og begrænsning for physics under transformerede parents er beskrevet i [ADR 0018](docs/decisions/0018-runtime-component-lifecycle-and-2d-physics.md).
- [x] **T207 — Tilemap-editor.** Afhænger af T206. `Tilemap2D` gemmer validerede lag/celler og assetbaserede tiles i scenen; WebGL udvider synlige celler til sprite-items, fire-retningers nabomasker vælger eksplicitte tilevarianter, og lag kan oprettes/fjernes samt skifte synlighed og kollision. Brush og flood fill registreres som undo/redo-handlinger; collidable celler bliver faste Rapier-boxes i Play. Rendering-unit-tests (8), typecheck, produktionsbuild og Chromium tilemap-workflowtest bestået; den eksisterende Chromium-suite (27 checks) bestod før den nye fokuserede workflowtest. Begrænsninger: ét billedasset pr. tile, variantmapping redigeres i tiledefinitionernes JSON, og colliderflader samles ikke. Se [ADR 0019](docs/decisions/0019-tilemap-format-and-collisions.md).
- [x] **T208 — Spriteanimation og tidslinjer.** `SpriteAnimation2D` gemmer klip med loop, spriteframes og schema-adresserede property-tracks. Animation-panelet kan oprette/fjerne klip, tilføje frames og keyframes, justere varighed/loop/autoplay og gemmer gennem sceneformat/projektlagring. Runtime interpolerer numeriske værdier, skifter andre scalar-værdier ved keys og opdaterer Game-viewets assettekstur. Scripts kører før animation, så animation vinder for trackede felter; Rapier skriver transforms efterfølgende og ejer dem på aktive fysikobjekter. Rendering-/animation-unit-tests (9), typecheck, produktionsbuild og alle Chromium-tests (30) passerer; E2E afprøver clip/frame/key-redigering, Play og reload-gendannelse. Nested property paths og editorens live timeline-scrubbing er ikke med. Se [ADR 0020](docs/decisions/0020-sprite-animation-and-property-timelines.md).
- [x] **T212 — Scene-bundne scripts og per-entity Play-runtime.** Afhænger af T201–T206. Sceneobjekter kan have versionsmærkede Script Binding-komponenter med code/graph paths og schema-validerede properties; kode bruger livscyklusfunktionerne `onStart`, `onUpdate` og `onStop`, mens ældre scenes migreres væk fra `entryFunction`. Inspector kan tilføje/fjerne bindinger. Play opretter uafhængig state/subscriptions pr. binding, kører bindings i stabil entity-ID-rækkefølge med fælles tick-snapshot og leverer events ved næste tick. Script-API'en har eksplicit adgang via stabile entity-ID'er; schema-validerede komponentkommandoer valideres samlet og anvendes efter invokationerne. Stop kasserer Play-kopien. Scene-roundtrip, migration, tværobjekt-command-buffer og browserflow med to scripts/bindinger er afprøvet. Valg dokumenteret i [ADR 0021](docs/decisions/0021-scene-bound-script-bindings.md). Validering: `npm run build`, scripting-tests, editor-unit-tests og Chromium-browsertests via Docker.
- [x] **T209 — Lyd.** `@ecs/audio` bygger på Web Audio med `AudioSource2D`, musik-/effektgrupper, Master-gain, asset-preview og Play-unlock. Kode og noder styrer sources med `audio.play`/`audio.stop` events. AudioSource schema/scene-roundtrip, mixerens routing, gain, cache, stop og dispose er dækket af unit-tests; Chromium-flowet afprøver WAV-import, preview, source-konfiguration, mixergruppe og browserens brugerinteraktion. `npm run build`, 2 audio-tests og alle 33 Chromium-tests passerer via Docker. Eksport-runtime kobles på i T304. Se [ADR 0022](docs/decisions/0022-web-audio-mixer.md).
- [x] **T210 — UI til spil.** `@ecs/ui` leverer schema-baserede `UiCanvas`, `UiText`, `UiImage` og `UiButton`; Inspector kan tilføje, fjerne og redigere felterne, og assets vælges med billedtype. Game-viewet viser et DOM-overlay over WebGL med ankre, offsets og `fit`/`stretch` referenceopløsning. Touch-/pointeregnede knapper udsender `ui.button.clicked` med entity-ID; kode og nodegrafer bruger deres fælles event-API, og scripts kan ændre UI-komponenter under Play. Typecheck/build, 2 UI-layout-/scene-roundtrip-tests, 19 scripting-tests, 14 scene-tests, 10 editor-unit-tests og alle 34 Chromium-tests passerer via Docker. Afprøvet i desktop Chromium; fysisk mobilbrowser er ikke del af denne validering. Første UI har ikke rotation, clipping-grupper eller flow-layout. Se [ADR 0023](docs/decisions/0023-dom-game-ui.md).
- [x] **T211 — Udbyg eksempelspillet.** Afhænger af T204–T210 og T212. `ECS Studio Showcase` er et versioneret, genåbneligt editorprojekt med alle aktuelle scene-komponenter: Parent/hierarki, sprites, fysik/kollision, tilemap, animation, script binding, lydkilde og UI-canvas/tekst/billede/knap. Player styres af action-input; kode og nodegraf videresender positions-events, knapklik ændrer UI og afspiller en effekt, og animation/fysik kører samtidig. UI-knappen kan bruges med pointer/touch; gamepad-input håndteres af den fælles action-map. Den danske [komponent- og scriptmanual](apps/editor/public/manual.html) forklarer Inspector-felter, kode-API, eventflow og noder. Showcase-arkivet genereres fra `examples/showcase/`. Typecheck/build, projektets komponenter, Play-flow, Stop og genåbning er afprøvet; alle 35 Chromium-browserchecks består. Testet browser: desktop Chromium; fysisk mobil og gamepad er ikke afprøvet.

Exit: både begyndere og udviklere kan bygge et lille komplet 2D-spil gennem editoren.

## M3 — Bred første udgivelse

Afhænger af M2.

- [x] **T301 — Prefabs.** Assets-panelet kan gemme et valgt objekt med underhierarki som prefab, oprette instanser med nye entity-ID’er og remappe interne entity-referencer. `Update Source` snapshottet det oprindelige scenehierarki; `Update Instances` synkroniserer komponenter på koblede objekter og bevarer ændrede/tilføjede/fjernede komponenter som synlige, komponentgranulære overrides. Fjernelse af kilden bevarer instanserne og viser en brudt reference. Prefabs gemmes i projektformat v5; v1–v4 migreres til et tomt bibliotek. ADR 0024 beskriver modellen og grænserne. Typecheck/build, alle editor-unit-tests og alle 37 Chromium-tests bestået via Docker. Begrænsning: kildeopdatering synkroniserer ikke tilføjelse/fjernelse af underobjekter og understøtter ikke feltgranulære overrides.
- [x] **T302 — Plugin-API.** Versionsmærket editor-API (`1.0.0`) registrerer schemas, scriptdefinitioner, asset-importere og editorpaneler. `Hello Plugin` kan indlæses og fjernes fra editoren; setup-fejl ruller registreringer tilbage, og unload blokeres, mens plugin-komponentdata findes i scenen. Tillidsmodellen og afgrænsningen fra gameplay-script-sandboxen er dokumenteret. Typecheck/build, scene-tests, 19 editor-unit-tests og fokuseret plugin-browserflow bestået via Docker. Se [ADR 0027](docs/decisions/0027-editor-plugin-api.md) og [plugin-vejledningen](docs/plugins.md). Eksterne plugin-pakker og sandboxing er ikke med.
- [x] **T303 — Debugging og profiler.** Console har klikbare kildehenvisninger, read-only Inspector for valgte Play-entities, live system-/scriptmålinger og WebGL-renderstatistik. Pause/Resume og Step er afprøvet sammen med profilen i Showcase; enkelttrin øger simulationens tick præcis én gang.
